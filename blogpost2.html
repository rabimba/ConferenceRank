My research agent hallucinated a conference last week.

I asked it a simple question — "what are the strong systems venues with deadlines in the next two months?" — and it confidently returned a list. One venue had the wrong acceptance rate (off by 15 points). One deadline was from last year's cycle. And one conference, as far as I can tell, does not exist. The model wasn't dumb. It was doing what LLMs do when the ground truth isn't in the context: it filled the gap with plausible-sounding folklore.

This annoyed me more than it should have, because I had literally built the antidote. Last post I wrote about ConferenceRank — the open dataset I maintain with CORE ranks, SJR quartiles, decades of acceptance rates, and live deadlines for 12,769 venues. The data was all there, refreshed weekly, verified. My agent just had no way to reach it.

Agents don't need more training data about conferences. They need a way to look it up.

So I taught the site to talk to agents. Three layers, all static, all open.

Layer One: A Real API (That Isn't a Server)

The site is a static GitHub Pages export — no backend, and I intend to keep it that way. But "static" doesn't mean "unreadable." Every build now also emits a JSON API next to the HTML:

  • api/index.json — a manifest with a generatedAt timestamp (so caches can revalidate) and counts
  • api/conferences.json — all 987 conferences with rank history, stats, deadlines, topics
  • api/journals-index.json + letter-chunked api/journals/{a-z}.json — all 11,782 journals
  • api/deadlines.json — upcoming deadlines only, flattened, chronological, abstract cutoffs included

Any HTTP client can read it. No auth, no rate limit, no key signup dance. The same weekly GitHub Actions run that refreshes the data regenerates the API, so agents always see what the website shows.

Layer Two: The MCP Server

Raw JSON is fine for scripts. For agents, the right interface is MCP — the Model Context Protocol, the closest thing we have to a standard tool-socket for AI assistants. So I packaged one: conferencerank-mcp.

Six tools:

search_venues

Free-text search over title, acronym, publisher, ISSN — with rank-tier and discipline filters.

get_venue

Full dossier: rank history across CORE editions, per-year acceptance stats, SJR trajectory back to 1999.

compare_venues

Side-by-side: ranks, rates, H-index, deadlines. The "NeurIPS vs ICML vs AAAI" question, answered with data.

suggest_venues

Paste an abstract, get ranked targets with reasons — the same TF-IDF + lexicon engine as the site's suggester, with stretch/target/safe tiering.

upcoming_deadlines

Deadlines in a forward window, AoE-normalized, filterable by tier and field — in paper or abstract mode, because missing abstract registration kills the submission.

acceptance_stats

The full year-by-year selectivity history for one venue. SOSP: 14 years of it.

Setup is one line. Claude Code:

claude mcp add conferencerank -- npx -y conferencerank-mcp

Or in any MCP host's config (Claude Desktop, opencode, etc.):

{
  "mcpServers": {
    "conferencerank": {
      "command": "npx",
      "args": ["-y", "conferencerank-mcp"]
    }
  }
}

On first call the server downloads the dataset and caches it under ~/.cache/conferencerank/, revalidating against the manifest timestamp. After that it's instant — and it works offline against the stale cache. True to the site's philosophy: your unpublished abstract never touches anyone's server. The suggester runs on the agent's machine, not mine.

Layer Three: A Skill for Everything Else

Not every agent speaks MCP. For the rest, there's a skill file — a plain SKILL.md that teaches any agent (Claude Code, opencode, Cursor, whatever reads skills) how to query the static API directly: which endpoint to fetch, how to resolve a journal's letter-chunk, how to interpret CORE vs. SJR, why the abstract deadline matters, and the predatory-venue heuristic (absent from both indexes + unknown publisher = red flag, say so).

And for agents that find the site organically: llms.txt and llms-full.txt ship at the root, documenting endpoints, schemas, and licensing.

Why This Matters Beyond My Tool

The pattern here is bigger than conference rankings. The next wave of useful agents won't be the ones with the biggest context windows — it'll be the ones plugged into curated, fresh, ground-truth data. Every niche dataset maintainer is sitting on something an agent could use, and most of those datasets are trapped behind HTML meant for human eyeballs.

The recipe I landed on is cheap enough for any side project: static JSON next to your HTML, a thin MCP wrapper that caches it, a skill file for everything else. Total new infrastructure cost: zero dollars. It runs on GitHub Pages.

If your data answers a question people ask agents, give the agents a door. They'll stop hallucinating the answer.
